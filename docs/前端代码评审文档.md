## 一、数据源模块评审

### 1.1 模块概述

| 文件 | 职责 |
|------|------|
| `src/services/dataSource.ts` | 数据源 CRUD API 服务层 |
| `src/components/DataSourceSelect/index.tsx` | 数据源下拉选择器 |
| `src/pages/DataSourcePage/index.tsx` | 数据源管理页面（增删改查） |
| `src/components/ConfigDialog/configs/dataSourceHelpers.ts` | 配置辅助函数（工具层） |
| `src/utils/queryFilter.ts` | 查询过滤器数据处理工具 |
| 各 `configs/*.tsx` | 轮播图、图表等组件的数据配置面板 |

### 1.2 亮点

- **类型定义完整**：`DataSourceItem` 接口覆盖了名称、HTTP方法、URL、请求头/参数/Body、分页等完整字段，无隐式 `any`
- **向后兼容处理**：`normalizeDataSourceMode` 函数对旧数据 `api` 值做了兼容迁移，避免存量数据失效
- **数据源复用**：通过 `DataSourceSelect` 组件统一选择界面，选中后自动填充 endpoint、method、headers、timeout 等字段，减少用户重复配置
- **Mock 覆盖完整**：列表/详情/创建/更新/删除全套接口均已实现

### 1.3 问题与建议

**问题 1：URL 字段无校验**

数据源创建/更新时 `url` 字段直接透传，无格式校验，存在保存无效地址的风险。

```typescript
// src/services/dataSource.ts
// createDataSource / updateDataSource 中 url 未校验
```

**建议**：添加 URL 格式校验（Protocol + Host 必填，路径可为空），防止保存无效地址。

---

**问题 2：数据源列表无分页**

`getDataSourceList` 返回全量列表，数据量大时存在性能风险。

```typescript
// src/services/dataSource.ts - getDataSourceList
// 返回全量列表，无分页参数
```

**建议**：后端支持分页参数（page/size），前端增加分页加载逻辑。

---

**问题 3：`queryFilter.ts` 中存在隐式 any**

`resolveQueryFilterOptionList` 中对 `object` 类型未做类型约束。

```typescript
// src/utils/queryFilter.ts
// 对 object 类型缺少约束
```

**建议**：补充 `Record<string, unknown>` 约束，避免运行时错误。

---

**问题 4：超时时间单位不一致**

- `dataSource.ts` 中 `timeout` 单位为**秒**
- `dataSourceHelpers.ts` 中转换为**毫秒**（`* 1000`）

```typescript
// dataSource.ts - timeout: number (秒)
timeout: number  // seconds

// dataSourceHelpers.ts - 转为毫秒
timeout: dataSource.timeout ? dataSource.timeout * 1000 : undefined
```

**建议**：统一在 API 层做单位转换，或在类型中明确标注单位（如 `timeoutSeconds: number`）。

## 二、全局配置模块评审

### 2.1 模块概述

| 文件 | 职责 |
|------|------|
| `src/services/globalConfig.ts` | 全局配置 API 服务层 |
| `src/store/useGlobalConfigStore.ts` | Zustand 状态管理（含防重入加载） |
| `src/utils/global-config.ts` | 纯函数工具集 |
| `src/pages/GlobalConfigPage/index.tsx` | 全局配置管理页面 |
| `src/components/BackgroundSettings/index.tsx` | 背景设置组件 |
| `src/components/WidgetTitleSettings/index.tsx` | 标题样式设置组件 |
| `src/components/GlobalThemeReferenceFields/index.tsx` | 引用全局配置的通用控件 |

### 2.2 亮点

- **防重入加载设计**：`useGlobalConfigStore` 中通过 `loadingPromise` 单例模式防止并发重复请求，这是一个值得推广的好设计，避免了多个组件同时挂载时触发多次请求。

  ```typescript
  // src/store/useGlobalConfigStore.ts
  const load = async () => {
    if (loadingPromise) return loadingPromise
    loadingPromise = api().finally(() => { loadingPromise = null })
    return loadingPromise
  }
  ```

- **兜底容错逻辑**：当 `documentStorageUrl` 为空时，自动回退到 `window.__APP_CONFIG__.MINIO_API_URL`，保障了无网络环境下的可用性。

- **工具函数纯净化**：`utils/global-config.ts` 中的函数（如 `getGlobalThemeScheme`、`buildBackgroundFormValues`）均为纯函数，无副作用，便于测试和复用。

- **"引用全局配置"抽象复用**：`GlobalThemeReferenceFields` 组件将开关+下拉框的交互模式抽离为通用组件，被 `ConfigDialog` 和 `DashboardConfigDialog` 共用，减少了代码重复。

- **Mock 服务状态持久化**：`mock/config/global-config-state.js` 支持从 compose `.env` 文件自动解析 OpenCode 地址，增强了开发环境的灵活性。

### 2.3 问题与建议

**问题 1：主题删除无激活状态校验**

删除主题时仅检查"至少保留一个主题"，但未校验删除的是否为"当前正在使用"的主题，可能导致用户丢失当前激活样式。

```javascript
// mock/routes/global-config.js - deleteThemeScheme
// 仅检查至少保留一个，未检查当前激活状态
```

**建议**：删除前检查当前激活主题，若删除正在使用的主题应提示用户切换。

---

**问题 2：颜色值格式化分散**

`GlobalConfigPage/index.tsx` 中的 `normalizeColorValue` 与 `ConfigDialog` 中可能存在的类似逻辑未收敛。

```typescript
// GlobalConfigPage/index.tsx 使用 normalizeColorValue
// ConfigDialog 中也可能有类似逻辑
```

**建议**：统一在 `global-config.ts` 工具层处理颜色格式化收敛，避免散落在各页面。

---

**问题 3：`useCanvasTheme.ts` hook 命名模糊**

当前命名与 `useGlobalConfigStore` 的职责边界不够清晰。

```typescript
// src/hooks/useCanvasTheme.ts
// 命名与实际功能对应关系不直观
```

**建议**：重命名为 `useDashboardTheme` 或 `useCanvasStyleTokens`，使其职责边界更清晰。

---

**问题 4：消息文案无平台兜底**

平台默认值硬编码在工具函数中，未统一收敛。

```typescript
// getGlobalMessageCopy 中平台兜底值硬编码
```

**建议**：平台默认值应统一收敛到常量文件或配置中，避免散落。

## 三、AI 助手模块评审

### 3.1 模块概述

| 文件 | 职责 |
|------|------|
| `src/services/agent-chat.ts` | AI 对话 API + SSE 流式处理 |
| `src/store/useWorkspaceAiAssistantStore.ts` | AI 状态管理（Zustand） |
| `src/components/AIAssistantPanel/index.tsx` | AI 对话面板主组件 |
| `src/components/WorkspaceAiFloatingCard/index.tsx` | AI 悬浮卡片（最小化状态） |
| `src/components/FloatingModule/components/AssistantHubComponent/` | 助手中心组件 |
| `src/components/FloatingModule/components/ChatComponent/` | 在线客服聊天组件 |
| `src/pages/Layout/index.tsx` | AI 状态集成与导航守卫 |

### 3.2 亮点

- **SSE 流式交互完善**：`agent-chat.ts` 完整实现了 EventSource 流式接口，支持 `status`、`reply_delta`、`thinking_delta`、`reasoning`、`message`、`error`、`done` 等多种事件类型，交互丰富。

- **打字机效果**：`AIAssistantPanel` 中通过累积显示内容实现打字机效果，用户体验流畅。

- **导航守卫机制**：`Layout/index.tsx` 中通过 `hasActiveAiRequest` 检测 AI 运行状态，防止用户导航时丢失正在生成的工作台内容：

  ```typescript
  // src/pages/Layout/index.tsx
  const hasActiveAiRequest = isDashboardRoute && (aiSending || Boolean(aiAbortController))
  ```

  这是很好的用户体验设计。

- **AbortController 支持**：用户可以主动停止 AI 生成，提供了良好的控���感。

- **会话上下文传递**：支持 `conversationId` 和 `messages` 参数，实现多轮对话上下文管理。

- **占位与 Loading 状态**：用户发送消息后立即创建 user 和 assistant 占位消息，配合 `status: 'loading'` 状态，避免 UI 闪烁。

### 3.3 问题与建议

**问题 1：`ChatComponent` 为纯前端模拟，未对接真实 AI 服务**

```typescript
// src/components/FloatingModule/components/ChatComponent/index.tsx
// onSendMessage 为空函数，需要外部传入回调
// 注释说明"待接入真实 AI 接口"
```

**建议**：尽快对接 `agent-chat.ts` 服务，或在未对接时通过 Config 配置控制显示/隐藏该模块。

---

**问题 2：`AssistantHubComponent` 中存在未完成的组件**

```typescript
// help/calendar/notes/custom 均为空占位
// <div>帮助文档组件(待开发)</div>
```

**建议**：使用条件渲染或配置隐藏未完成入口，避免用户点击后看到占位内容。

---

**问题 3：SSE 错误处理未分级**

`agent-chat.ts` 中 `error` 事件统一触发，未区分网络错误、服务端错误、Token 过期等不同场景。

```typescript
// src/services/agent-chat.ts
// error 事件统一触发，未分级处理
```

**建议**：根据错误类型提供差异化提示（如 Token 过期引导重新登录）。

---

**问题 4：`useWorkspaceAiAssistantStore` 中 `reset` 函数风险**

`abortController.abort()` 后清空 messages，可能丢失用户未保存的内容。

```typescript
// 重置前未确认，可能丢失数据
```

**建议**：重置前增加确认对话框，参考 Layout 中的 `confirmAbortAiRequest` 模式。

---

**问题 5：快捷提示语硬编码**

```typescript
// src/components/AIAssistantPanel/index.tsx
const DEFAULT_PROMPT_SUGGESTIONS = [
  '生成一个简洁的运营看板，包含标题、KPI 指标卡、趋势图和数据表格。',
  // ...
]
```

**建议**：支持从配置文件读取，便于运营调整提示语。

## 四、整体评审总结

### 4.1 评分

| 维度 | 评分 | 说明 |
|------|------|------|
| 代码规范 | ⭐⭐⭐⭐ | TypeScript 覆盖率高，命名清晰，结构规范 |
| 架构设计 | ⭐⭐⭐⭐ | 分层清晰（服务层/状态层/工具层/组件层），但模块边界偶有模糊 |
| 类型安全 | ⭐⭐⭐⭐ | 类型定义完整，部分辅助函数存在隐式 any |
| 可维护性 | ⭐⭐⭐⭐ | 组件拆分合理，工具函数纯净化程度高 |
| 安全性 | ⭐⭐⭐ | 数据源 URL、请求参数均未做 XSS 过滤；AI 对话内容未做敏感词过滤 |
| 性能 | ⭐⭐⭐⭐ | RAF 优化、Zustand 防重入、useMemo/useCallback 使用得当 |

### 4.2 跨模块共性问题

1. **类型命名不一致**：部分数据源相关类型分散在 `types/index.ts`、`ConfigDialog/configs/types.ts`、`utils/queryFilter.ts` 中，建议统一收敛到 `src/types/dataSource.ts`。

2. **Mock 与生产代码耦合**：全局配置的 mock 服务读取了 `process.env`，但生产环境变量通过 `window.__APP_CONFIG__` 注入，两套机制不统一。

3. **未完成功能暴露**：`ChatComponent`、`AssistantHubComponent` 中有多个"待开发"占位，建议通过 Feature Flag 控制显示。

### 4.3 优先改进建议

| 优先级 | 模块 | 问题 | 改进方案 |
|--------|------|------|----------|
| 高 | 全局配置 | 主题删除无激活状态校验 | 删除前检查当前主题，提示切换 |
| 高 | AI助手 | 未区分 SSE 错误类型 | 分级错误处理 + 差异化提示 |
| 中 | 数据源 | URL 无格式校验 | 添加正则校验 |
| 中 | AI助手 | ChatComponent 未对接真实服务 | 对接 agent-chat 或条件隐藏 |
| 低 | 数据源 | 列表无分页 | 接入后端分页接口 |
| 低 | 全局配置 | 颜色格式化分散 | 统一收敛到工具函数 |
